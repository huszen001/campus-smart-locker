## 一、系统工作原理

系统由「现场设备侧」与「云端服务侧」两部分构成，中间通过 MQTT 消息总线连接，
整体是一个「认证 → 授权 → 下发命令 → 执行 → 反馈 → 落库」的闭环。

### 现场设备侧（柜体）

**柜子做 4 格，但硬件只够一格** —— 下面这几样要分成两类看：

| 类别 | 器件 | 装了几套 | 后果 |
|---|---|---|---|
| **柜体级** | ESP32 主控、MFRC522 读卡器、0.96″ OLED | 1 套，全柜共用 | 读卡器**不知道**你站在哪一格前；屏幕只能轮流显示各格状态 |
| **柜格级** | SG90 舵机、干簧管门磁、HX711 压力传感器 | 只装了 **1 号格** | 2~4 号格没有任何硬件，由固件**虚拟** |

（舵机 + 门磁 + 秤是 4 根线，四格要 16 根，这块板子伸出来的可用脚不够。）

- **校园卡（RFID）**：13.56 MHz、ISO14443A 无源卡，卡内芯片存唯一 UID 序列号。
- **MFRC522 读卡模块**：经 SPI 与 ESP32 通信，发射电磁场让卡无源取电并回传 UID。**只吃 3.3V。**
  **全柜就这一个**，所以它读到的只是一张卡 —— "刷哪一格"由后端按卡主算（见第三节）。
- **ESP32 主控**：Wi-Fi 联网、运行 MQTT 客户端，发布 `status` / `event`，
  订阅 `cmd` / `auth_result`。**它只执行命令，不判断权限** —— 所有授权判定都在后端。
  一块板子上跑 **4 格各自的状态机**。
- **SG90 舵机 + 干簧管门磁**（1 号格）：舵机旋转模拟上锁 / 开锁；门磁检测门**真正**开没开。
  这两者是分开的，`舵机开锁 ≠ 门被打开`，这个区别是全系统的要害（见第四节）。
- **HX711 + 压力传感器**（1 号格）：柜格底部，**只回答"有没有东西"，不称重**，
  所以不上报克数、屏幕上也只有"物有 / 物无"。
- **0.96″ OLED 状态屏**（柜体级）：只有一块屏，所以**在 4 格之间轮放**
  （每 2 秒翻一页，带 `1/4` 页码），刷卡和开门时插播一条反馈并锁定在被点到的那一格。
- **2~4 号格（虚拟）**：没有舵机、没有门磁、没有秤。固件自己演：收到开门命令后设一个
  3 秒的计时器，到点自己发 `door_opened`、再发 `door_closed`，格内有物与否按动作直接置位。
  **报文格式与真机完全一致**，后端一行都不用改 —— 这就是"一套硬件做出多格效果"的做法。

### 云端服务侧（服务器）

- **微信扫一扫打开的 H5 页面**：存件、取件、注册、绑卡。**不是小程序**，是 H5。
- **网页监控台**：柜格状态、订单、操作日志，需要管理口令。
- **Flask 后端**：注册 / 绑卡、授权判定、订单状态机、MQTT 接入、审计日志、二维码与柜贴。
- **SQLite（`locker.db`）**：`users` / `orders` / `audit` **三张表**。
  注意**没有"柜体表"** —— 柜格的实时状态在内存里，靠设备心跳重建。

### 两条入口、一套判定

两条路径在 Flask 后端汇合，共用同一套授权判定，再经 MQTT 下发 `cmd`：

1. **扫码路径**：微信扫柜贴二维码 → H5 页面 → `POST /api/open` → Flask。
2. **刷卡路径**：卡片 → MFRC522 读 UID → ESP32 发 `card_scan` → Flask。

### 核心原理

- **RFID 卡识别**：读卡器发电磁场，卡无源取电回传 UID，作为身份凭证。
- **MQTT 发布 / 订阅**：设备与后端不直接互调，均接入 broker 按主题通信，实现松耦合。
- **开锁–反馈闭环**：**后端不因为"命令发出去了"就认为存取成功** ——
  设备必须回 `door_opened` / `door_closed`，后端才认。这是"防执行失败"的全部依据。

## 二、系统总体架构（四层）

自上而下四层，上行传数据、下行传命令：

- **交互层**：微信扫一扫打开的 H5 页面（存件、取件、注册、绑卡）、
  网页监控台（运营看板、状态监控、订单、日志）、
  柜贴二维码**两种**（柜体总码 `/poster/cabinet`、柜格贴 `/poster/<box>`，都可打印）、
  校园卡刷卡开柜。
- **后端层**：用户管理（注册、绑卡）、授权判定（防越权）、**定格**
  （扫总码时挑格 / 凭码找格 / 刷卡按卡主算格）、订单状态机、
  MQTT 接入、审计日志、数据存储（SQLite 三张表）。
- **传输层**：MQTT Broker（Mosquitto，局域网 `0.0.0.0:1883`，强制用户名密码）、
  主题规范（`locker/locker1/` 下 `cmd` / `status` / `event` / `auth_result`）、
  JSON 报文格式、Wi-Fi 接入与每 10s 心跳保活。
- **设备层**（**×1 的是全柜共用**）：ESP32 主控 ×1（跑 4 格状态机）、
  MFRC522 读卡 ×1（柜体级）、0.96″ OLED ×1（柜体级，4 格轮放）、
  SG90 舵机 ×1 / 干簧管门磁 ×1 / HX711 压力传感器 ×1（**柜格级，只装在 1 号格**），
  2~4 号格由固件虚拟。

**两侧贯穿**

- **安全机制**：手机号 / 取件码 / 卡 UID 三种凭证、防越权判定、管理口令、
  审计日志、失败路径兜底。
- **协议与数据**：MQTT 3.1.1、JSON、HTTP RESTful、ISO14443A、SPI、软件 I2C。

**数据流向**

- 上行：设备层 → 传输层 → 后端层 → 交互层（`status`、`event`、`card_scan`）。
- 下行：交互层 → 后端层 → 传输层 → 设备层（`cmd`、`auth_result`）。

## 三、存取件业务流程

### 先说清楚：格号是怎么定下来的

柜贴有**两种**，这是理解后面流程的前提：

| | 柜体总码 `/scan` | 柜格贴 `/scan?box=N` |
|---|---|---|
| 张数 | 1 张，贴柜子正面 | 每格 1 张 |
| 存件 | **后端自动挑格**（`pick_free_box`） | 就存进这一格 |
| 取件 | **凭码自己找格**（`box_of_code`） | 码必须属于这一格，否则 403（格是空的则 409） |

**挑格规则**：只在**在线**的格里挑，取**格号最小**的空格。四格都在线且都空时，第一单落 1 号格。
"空格"用 `occupant()` 判定 —— 这是全项目**唯一**一个"这格里现在有没有东西"的口径。

**⚠️ 格号非法一律报错，绝不静默回落。** 旧写法是 `data.get("box", 1)`，单格时看不出区别，
多格之后等于"扫 3 号格、开 1 号格的门"，用户放进去的东西躺在别人的格里，
而页面上写着"3 号"—— 事后谁都说不清。所以 `/api/open` 里格号不存在回 400，
`/scan?box=9` 回 404；门磁回执里的格号无效，整条丢掉并记一条 `deny` 审计。

### 存件

1. 用户扫二维码（总码或柜格贴），在 H5 填**手机号**，点存件。
2. 后端查 `users`：这个手机号注册过吗？
   - 没注册 → 拒绝（403），**页面直接跳到注册页并把手机号填好**（只弹一句话的话，
     新用户站在那儿没路可走 —— 注册入口在「我的」页里，他得自己一路找回去）。
   - 注册过 → 继续。
3. **定格**：扫的是柜格贴就用那个格；扫的是总码，就
   **先在事务外取一张"在线格快照"，再从中挑一个空格**（格号最小的）。
   挑不出来（四格都占了 / 一格都不在线）→ 拒绝（409 没有空闲柜格 / 503 设备离线）。
4. 后端复查该格占用状态：**这一格现在是空的吗？**
   - 已有物 → 拒绝（409 `already_occupied`）。
   - 是空的 → 继续。
5. **建订单 `pending` 并落库，然后才发布 `cmd`**（顺序不能反，理由见第五节）。
   到这一步格号才真正定下来，报文里也才带上 `box`。
6. 设备收到命令，**先做一次防呆复检**（1 号格用压力传感器；虚拟格跳过），
   然后舵机开锁、置 `ST_OPEN`。
7. **决策点一（防执行失败）**：门真的被打开了吗？
   - 15 秒内没有 → 订单判 `failed`（`OPEN_ACK_TIMEOUT`）。
   - 有 → 设备回 `door_opened`，订单转 `opened`。
8. 用户放入物品，关上门。设备检测到门关，**再读一次压力传感器**判定柜格状态
   （虚拟格没有秤，按"这次是存件"直接置成有物）。
9. **决策点二**：门关上了吗？
   - 60 秒内没有 → 订单判 `failed`（`OPEN_CLOSE_TIMEOUT`），设备另报 `door_left_open`。
   - 有 → 设备回 `door_closed`，订单转 `done`。
10. 后端**生成 6 位取件码**，大字回显给用户（扫总码时还会告诉他在几号格），并写审计日志。

### 取件

同一条流程，几处不同：

- 凭证从**手机号**换成 **6 位取件码**。
- **扫总码时页面上根本没有格号**：后端拿着码去**每一格**调 `occupant()` 核对，
  对上哪一格就是哪一格（`box_of_code`）；哪一格都对不上 → 403 取件码不对。
- **⚠️ 不能直接 `SELECT box FROM orders WHERE pickup_code=?`**：那样一个早就取走的存件单
  还会命中，于是给用户开一次空柜门。宁可多查几次 `occupant()`，也不要第二个口径。
- 占用状态检查反过来：取件要求**该格有物**，空柜取件报 409 `nothing_to_pickup`。
- 关门后压力传感器应测到**空** → 柜格回到 `IDLE`；同时后端按
  "取件关门时刻 − 存件关门时刻"结算扣费。
- 找不到格和"格是空的"回的是**同一句话、同一个状态码**：存件码只有 6 位，
  分开报等于给别人一个枚举的口子。
- **取件不校验是谁来取** —— 码就是凭证，朋友拿码也能取走，这是有意为之。

### 刷卡路径

**RC522 是柜体级的，它读到的只是一张卡，卡不会说"我在 3 号格前"。**
所以"刷哪一格"是**后端按卡主算出来的**：

- 这张卡的主人**占着哪一格** → 就是取件，开那一格。
- 哪一格都没占 → 就是存件，格从在线的空格里挑（和扫总码**完全走同一条路**）。

所以报文里的格号**被忽略**（设备侧也不再发）。顺带一个好处：早先那条
"卡主不是这格占用者"的拒绝分支（`not_owner`）**整条消失了** ——
格是按卡主自己算出来的，算出来的格不可能是别人占着的。

另外几条：卡还没绑 → 走 45 秒绑卡窗口那条老路；卡主欠费 → 拒绝存件（`reason: balance`）；
一件设备都没在线 → 拒绝（`device_offline`）；没空格 → 拒绝（`reason: full`）。

> **⚠️ 全系统的要害是两个决策点**
> 一个是**防越权**（凭证对不上就拒），一个是**防执行失败**（门磁说了算）。
> 只做前者，柜子会"命令一发就当成功"；只做后者，别人能随便开你的柜。

## 四、柜格状态机（设备端）

**每一格各跑一份**（固件里是 `Box boxes[BOX_COUNT]`），四格互不影响。
下面这套状态机对四格是同一套，唯一的区别在"门真的被打开了吗"这一步怎么判定：

- **1 号格**：有真簧片，`doorSeenOpen` 防呆照常 —— 没见过门开就不认门关。
- **2~4 号格**：没有硬件可读，`doOpen()` 走另一条分支，设一个 `closeAt = now + 3s`，
  到点自己发 `door_opened` 再发 `door_closed`，格内有无按动作直接置位。

### 三个状态

- **IDLE（空闲）**：门关、已上锁、**无物**。常态，可接受存件。
- **OPEN（门已开）**：已解锁，等用户开门。短暂中间态。
- **OCCUPIED（有物品）**：门关、已上锁、**有物**。

### 状态迁移

- 上电初始化：**1 号格**读一次压力传感器 —— 有物 → `OCCUPIED`，无物 → `IDLE`。
  （初态不是固定的，这样断电恢复后状态才不会错乱。）虚拟格没有秤可读，一律从 `IDLE / 无物` 起步。
- `IDLE → OPEN`：收到 `cmd:open`（存件）。
- `OCCUPIED → OPEN`：收到 `cmd:open`（取件）。
- `OPEN → IDLE`：**门被打开过** 且 关门后测到**空**。
- `OPEN → OCCUPIED`：**门被打开过** 且 关门后测到**有物**。
- `OPEN` 超过 30 秒未关门 → 上报 `error(door_left_open)`，**但状态不迁移，仍在 `OPEN`**。

### 四条要注意的

1. **⚠️ 这里只有三个状态，网上常见的第四个 `ERROR` 在本项目是死代码。**
   固件里 `ST_ERROR` 仅作枚举占位，代码不会进入它 —— 后端靠自己的超时判 `failed`
   来兜"执行失败"，设备端不需要故障态。硬要启用会出事：关门分支的条件是
   `boxes[n].state == ST_OPEN && !doorOpenOf(n)`，一旦进了 `ST_ERROR` 就再也匹配不上，
   状态会**永久卡死，只能重启**。

2. **⚠️ `OCCUPIED` 是只进不出的**：只能靠一次正常的取件（`OCCUPIED → OPEN → IDLE`）
   才会离开。这正是"柜里有东西就存不进去"这个防呆的来源 ——
   它是状态机天然带来的，不是额外写的判断。

3. **⚠️ 关门回执之前，门必须真的被打开过**（固件里的 `doorSeenOpen`，**只有 1 号格有**）。
   **舵机开锁 ≠ 门被打开**：下单时若门正好关着，程序置 `ST_OPEN` 后下一轮（50 ms）
   就会把"锁已开"当成"门关了"，订单 1 秒就 `done`，而东西还没放进去 ——
   那一刻压力传感器读到无物，状态还会落成 `IDLE`，
   于是柜里明明有东西、状态却说空。真机流程必须是
   **下单 → 舵机开锁 → 手动拉开门 → 放东西 → 关门**。
   （虚拟格没有簧片可读，这一步不适用 —— 它是靠 3 秒计时器自演开门/关门的。）

4. **`OPEN` 超时只上报、不迁移状态**。30 秒没关门会发一条 `error` 事件让后端和审计知道，
   但柜格仍留在 `OPEN` 等用户 —— 强行转移反而会把人锁在外面。

## 五、订单状态机（后端）

### 四个状态

```
pending ──door_opened──> opened ──door_closed──> done
   │                        │
   └─ 15s 超时 ─────────────┴─ 60s 超时 ──────> failed
```

- **`pending`**：已下发开门命令，等设备确认。
  设备离线、或 MQTT 发布失败 → 直接 `failed`。
- **`opened`**：门确实开了，等用户关门。
- **`done`**：门关了、落库。**存件在这一刻生成 6 位取件码。**
- **`failed`**：两种超时之一触发。

### 关键点

- **`done` 必须等到门磁回执**。后端不因为"命令发出去了"就认为存/取成功 ——
  设备可能根本没开门，或者开了没人关门。这是"防执行失败"的落点。
- 两个超时可用环境变量调：`OPEN_ACK_TIMEOUT`（默认 15 秒）、
  `OPEN_CLOSE_TIMEOUT`（默认 60 秒）。
- **命令先落库再 publish**。设备最快毫秒级就回 `door_opened`，
  如果那时订单还没写进去，事件线程就不知道这条回执是谁的。
- **⚠️ 已知缺口：`advance()` 是"按格"推进的，不是"按单"。**
  它先从这一格里挑单（`WHERE box=? AND status=? ORDER BY id DESC LIMIT 1`），
  再做条件 UPDATE —— **"推进哪一张"是按格号挑的，因为门磁回执里没有订单号**。
  于是这个时序会出事：某格上一单的 `door_closed` 迟到，而该格此刻恰有**另一张**
  在 `opened` 的单，这张回执就会推错单（还会用错的 `closed_at` 去计费）。
  现实中要凑齐这个时序不容易，但它是真的。根因是 `publish_open()` 下发的 `cmd` 里
  其实带着 `order`，而**固件没把它带回回执**；修法是固件原样回传、`advance()` 改成按
  `id` 推进。**本次没做，只记在 README 的「已知缺口」里。**

## 六、三条时序

### 存件

扫二维码 → 填手机号 → 校验注册 →（**扫总码时：取在线快照 + `pick_free_box` 挑格**）→
复查该格是空的 → 建订单（**此刻格号才定**）→ 下发 `cmd{box}` →
舵机开锁 → **用户手动拉开门**（虚拟格跳过这步，3 秒后自己发）→ 设备回 `door_opened` →
用户放入物品并关门 → 设备判格状态（1 号格读压力传感器，虚拟格直接置位）→
回 `door_closed` → 订单 `done` → **回显 6 位取件码（+ 在几号格）**。

> ⚠️ **取件码只回给页面，从来没下发给设备** —— 所以柜体那块 OLED 上显示不了取件码。
> 要在屏幕上显示，得改后端协议（让 `/api/open` 之后把码发给设备），本项目没做。

### 取件

扫二维码 → 填 6 位取件码 →（**扫总码时：`box_of_code` 拿着码逐格核对，找到那一格**）→
校验码 → 建订单（**带 `store_id` 指回存件单**）→ 下发 `cmd{box}` → 舵机开锁 →
**用户手动拉开门** → 设备回 `door_opened` → 用户取出物品并关门 →
设备判格状态 → 回 `door_closed` → 订单 `done` → 按两个 `closed_at` 结算扣费 →
柜格回到 `IDLE`。

### 刷卡

**刷卡不区分存件 / 取件，也不必说"刷哪一格"** —— 后端按卡主自己算：

```
读到 UID → 查 users
  ├─ 没绑定 → 45 秒绑卡窗口还在？→ 是则绑卡（ok/card_bound），否则 deny/not_bound
  └─ 已绑定 → 卡主占着哪一格？
        ├─ 占着 N 号格 → 取件，格 = N
        └─ 哪格都没占 → 存件，从在线的空格里挑一个
              └─ 挑不出来 → deny/full（屏幕："柜子满了"）
     └─ 卡主欠费且是存件 → deny/balance
     └─ 一件设备都没在线 → deny/device_offline
     └─ 通过 → auth_result{ok} + cmd{box} → 开门
```

> **⚠️ 存件前先在事务外预检一次"还有没有空格"**。不然会出现
> "屏幕说『已授权，请放入物品』，然后门一声不响" —— 屏幕上那句谎话比多查一次库难看得多。

## 七、授权与安全（防越权）

三种凭证，三条判定 —— 但**"开哪一格"这件事本身也是判定的一部分**：

| 路径 | 凭证 | 校验规则 | 格号从哪来 |
|---|---|---|---|
| H5 存件 | 手机号 | 必须在 `users` 表里注册过 | 柜格贴 → 就是那一格；总码 → `pick_free_box()` 挑在线空格 |
| H5 取件 | **6 位取件码** | 必须对上某一格里那件东西的 `pickup_code`，否则 403 | 柜格贴 → 就是那一格；总码 → `box_of_code()` 逐格找 |
| 刷卡 | 校园卡 UID | 卡主**占着某一格**就取那一格；没占就从在线空格挑一格存 | 后端按卡主算，**报文的格号被忽略** |

**三条路最后都归一成同一个问题**：这一格里现在是空的吗 —— 由 `occupant()` 一个函数回答，
全项目**没有第二个口径**（挑空格、凭码找格、刷卡定格、取件校验、看板统计全都调它）。

**监控台和两个接口要管理口令**（`/`、`/api/orders`、`/api/logs`），
因为订单列表里有取件码，而**取件码是能开柜的** —— 不挡的话局域网里任何人
访问一下就能捞走所有人的手机号和取件码，整套授权当场作废。运营看板 `/api/stats`
也一并要口令（营收和单量是经营数据）。

**扫码页不查口令**，它只碰三样东西：`/api/boxes`（柜格状态，不敏感）、
`/api/order/<id>`（只回 `id/box/action/status/closed_at` **加一个算出来的 `fee_fen`**，
**故意不回手机号、取件码和 `store_id`** —— `fee_fen` 可以给，它只说明"这一单花了多少钱"，
泄漏不了谁存的、还剩多少余额）、以及 `/api/pay` 自助充值（**故意不查口令**：
用户自己给自己充，哪来的口令；代价是局域网里知道手机号就能给它充值，
课设里钱是假的，真实上线这条必须由支付平台的异步回调驱动）。
而且**扫码页不把手机号存进 localStorage** —— 这是共用柜子，页面每次打开都该是干净的。

## 八、数据库

`locker.db`（SQLite 单文件），**三张表**：

| 表 | 装什么 |
|---|---|
| `users` | 用户：姓名、手机号（UNIQUE）、绑定的卡 UID（UNIQUE） |
| `orders` | 订单：柜格、手机号、动作（`store`/`pickup`）、状态、**取件码**、创建/关闭时刻 |
| `audit` | 审计流水：时刻、来源、操作者、柜格、动作、结果（`ok`/`deny`）、详情 |

**没有"柜体 / 柜格"表** —— 柜格的实时状态（在线、门开、有物）在 Flask 的内存里，
靠设备每 10 秒的 `status` 心跳重建，重启后端即清空。这是有意的：
它就是设备的瞬时状态，落库反而要处理"断电后残留的脏状态"。

## 附：MQTT 主题与报文一览

设备 ID 为 `locker1`，四个主题都在 `locker/locker1/` 下：

| 主题 | 方向 | 报文 |
|---|---|---|
| `.../status` | 设备 → 后端 | **每格一条**（不是一条报文塞四格）：`{box, state, locked, door_open, item, ts}` |
| `.../event` | 设备 → 后端 | `{event, [box], ts, [reason]/[uid]}`，`event` ∈ `door_opened`/`door_closed`/`card_scan`/`error` |
| `.../cmd` | 后端 → 设备 | `{cmd:"open", box, action, order, ts}` |
| `.../auth_result` | 后端 → 设备 | `{result, [box], [action], [reason]}`，`result` ∈ `ok`/`deny` |

**几条容易看漏的**：

- **`card_scan` 报文里没有 `box`**，只有 `{event, uid, ts}` —— RC522 是柜体级设备，
  它读到的只是一张卡，**"刷的是哪一格"是后端按卡主算出来的**（见第六节"刷卡"）。
  固件里 `publishEvent(n=0, ...)` 的 `n==0` 就表示"这条事件不属于某一格"。
- **`cmd` 里有 `order`，但设备不回传** —— `door_opened`/`door_closed` 都只有 `box`。
  后端是靠"这一格最近一条 `pending` 单"来回填的，这也是 `advance()` **按格推进而非按单**
  的根本原因（见第五节关键点的 ⚠️）。
- **`auth_result` 的 `box` 可能是 `null`** —— 卡没绑定时后端还不知道是哪一格
  （`auth_result("ok", None, reason="card_bound")` 同理）。
- **`door_closed` 的 `box` 一定是 `REAL_BOX`（1 号格）**：门磁只有 1 号格有，
  虚拟格的关门回执是模拟出来的，走的是另一条分支。

> **⚠️ 报文里的 `ts` 不能用来判在线**：真实设备发的是 `millis()/1000`（开机秒数，几十到几百），
> 后端另存了一个 `last_seen = time.time()`，而且**只在 `status` 心跳里刷新** ——
> 事件消息不刷，否则一条 `card_scan` 就能让已经死掉的设备"续命"。
> （`device_sim.py` 发的 `ts` 是真实 epoch，**两边的 `ts` 根本不是同一种东西**，
> 所以更不能拿它算在线。）

> **⚠️ 已知缺口：MQTT 上没有"设备身份"。** 全项目只有一个账号
> `locker` / `locker123`，后端**信任任何发到 `locker/locker1/*` 上的人**，
> 而设备也**不校验 `cmd` 是不是后端发的**。所以在能连上 broker 的网络里，
> 谁都能假装成柜子发一条 `door_closed`，或者直接发一条 `cmd` 让舵机开锁。
> 课设里 broker 只监听本机、是够的；真上线必须加设备级凭证 + 主题 ACL，
> 细节写在 README 的「已知缺口」第 1 条。
