校园智能寄存柜 · 系统图集

课程设计原型　|　技术路线：ESP32 ＋ MFRC522 校园卡识别 ＋ SG90 舵机 ＋ 干簧管门磁 ＋ HX711 压力传感器 ＋ 0.96″ OLED ＋ MQTT（Mosquitto）＋ Flask ＋ SQLite

柜子做 4 格，但硬件只够一格：舵机 / 门磁 / 秤装在 1 号格，2~4 号格由固件虚拟（状态和开门时序都自己演， 报文格式与真机一致）；读卡器与屏幕是全柜共用的，所以「刷哪一格」由后端按卡主算出来。

配套文件：diagrams.md（同一套图的 Mermaid 源）、说明文字版.md（逐图文字讲解）。 图 6 / 图 7 / 图 8 三张时序图只在 Mermaid 版里提供 —— 手写 SVG 画时序图性价比太低，这一条沿用旧图集的做法。

图 1　系统工作原理图

两条入口（微信扫一扫打开的 H5 页面 / 校园卡刷卡）汇聚到后端，经 MQTT 下发开门命令；设备执行后经门磁反馈形成闭环。

要点：刷卡路径走「读 UID → 发布 card_scan → 后端查绑定」，扫码路径走「填手机号或取件码 → POST /api/open」； 两条路径在 Flask 后端汇合，共用同一套授权判定，再经 MQTT 下发 cmd。 门磁的回传让后端能确认「锁到底开没开」，而不是发完命令就了事 —— 这是状态闭环的关键。

⚠️ 柜子是 4 格，硬件只够一格。上面设备侧那一筐（舵机 / 门磁 / 秤 / 屏）是按 1 号格画的，而这几样分两类：

  • 柜格级（每格一套，只装了 1 号格）：SG90 舵机、干簧管门磁、HX711 压力传感器。 舵机 + 门磁 + 秤是 4 根线，四格要 16 根，这块板子的可用脚不够。
  • 柜体级（全柜共用一套）：ESP32 主控、MFRC522 读卡器、0.96″ OLED。 正因为读卡器是共用的，"刷哪一格"它根本不知道 —— 由后端按卡主占着哪一格算出来 （见 diagrams.md 图 8）。屏幕也只有一块，只能轮流显示 4 格状态。
2~4 号格由固件虚拟：状态、开门时序都自己演，报文格式与真机完全一致，后端一行都不用改。 所以监控台上看到它们「离线」是正常现象（真机运行时 2~4 号格没有心跳）。

⚠️ 与旧版的差别：

  • 交互层是 H5 页面，不是微信小程序。柜贴上的二维码被微信「扫一扫」打开，就是一个普通网页 —— 没有小程序那一套 appid、授权登录、审核发布。
  • 数据库是三张表不是四张。没有「柜体表」：柜格的在线/门开/有物是设备每 10 秒心跳上来的瞬时状态， 存在 Flask 内存里，重启后端即清空。落库反而要处理「断电后残留的脏状态」。
  • 设备只是执行器。ESP32 不做任何权限判断，全部判定在后端 —— 这样改固件绕不过授权。
  • 柜贴有两种。柜体总码 /poster/cabinet（一张，存件自动挑格、取件凭码找格） 和柜格贴 /poster/<box>（每格一张，锁定到那一格）。

图 2　系统总体架构图

四层架构：设备层 → 传输层 → 后端层 → 交互层；两侧为贯穿全系统的安全机制与协议/数据规范。

数据流向： 上行「设备层 → 传输层 → 后端层 → 交互层」跑的是 status（每 10s 心跳）、event（door_opened / door_closed / card_scan / error）； 下行「交互层 → 后端层 → 传输层 → 设备层」跑的是 cmd（开门命令）和 auth_result（刷卡授权结果）。

⚠️ 三处容易画错的地方：

  • 数据存储是 SQLite 三张表（users / orders / audit），旧图写的「SQLite / MySQL 四张表」里 那张「柜体表」从来就不存在 —— 柜格状态是心跳上来的瞬时量，只活在内存里。
  • 交互层没有「小程序」。是微信扫一扫打开的 H5 页面，写「小程序」会让人以为要 appid 和审核发布。
  • 设备层多了 HX711 与 OLED，少了一颗「光电传感器」。 物品检测已经从光电换成 HX711 压力传感器，但功能没变 —— 仍然只回答「有 / 无」，不称重。
  • 设备层现在标了「×1」和「柜体级 / 柜格级」。柜子做 4 格，但 舵机 / 门磁 / HX711 只装了 1 号格 （它们是柜格级的，每格一套），ESP32 / RC522 / OLED 是全柜共用的（柜体级）。 2~4 号格由固件虚拟，无硬件。

图 3　存取件业务流程图

存件走手机号、取件走 6 位取件码，两条支路在「建订单」处汇合；之后是同一套「下发命令 → 门磁确认 → 落库」闭环。格号在这两条支路上都是后端算出来的：扫柜体总码时存件由 pick_free_box() 挑、取件由 box_of_code() 找。

两个决策点是全系统的要害： 一个防越权（凭证对不上就拒，且记审计 —— 别人拿不走你的东西）， 一个防执行失败（门磁说了算：命令发出不等于柜门开了，更不等于东西放进去了）。

⚠️ 关门回执之前，门必须真的被打开过。固件里的 doorSeenOpen 就是干这个的：舵机开锁 ≠ 门被打开。 下单时若门正好关着，程序置 ST_OPEN 后下一轮（50 ms）就会把「锁已开」误判成「门关了」， 订单 1 秒就 done，而东西还没放进去 —— 那一刻压力传感器读到无物，状态还会落成 IDLE， 于是柜里明明有东西、状态却说空。真机流程必须是 下单 → 舵机开锁 → 手动拉开门 → 放东西 → 关门。

⚠️ 格号非法一律报错，绝不静默回落。旧写法是 data.get("box", 1)： 单格时看不出区别，多格之后等于「扫 3 号格、开 1 号格的门」 —— 用户放进去的东西躺在别人的格里，而页面上写着「3 号」，事后谁都说不清。 所以 /api/open 和 /scan 里，格号不存在就 400 / 404； 门磁回执里的格号无效，整条丢掉并记一条 deny 审计。 宁可丢一条回执让它超时失败，也不要记到别人头上。

凭码找格必须复用 occupant()，不能直接查 orders。 直接 SELECT box FROM orders WHERE pickup_code=? 的话， 一个早就取走的存件单还会命中，于是给用户开一次空柜门。 「这格里现在有没有东西」全项目只有 occupant() 一个口径 —— 挑空格、凭码找格、刷卡定格、看板统计全都调它。

图 4　柜格状态机（设备端）

只有三个状态。每一格各跑一份（固件里是 Box boxes[BOX_COUNT]），四格互不影响。左右两条竖线分别是「下行（进 OPEN）」与「上行（出 OPEN）」，避免箭头互相压住。

⚠️ 这里只有三个状态，网上常见的第四个 ERROR 在本项目是死代码。 固件里 ST_ERROR 仅作枚举占位，代码不会进入它 —— 后端靠自己的超时判 failed 来兜「执行失败」， 设备端不需要故障态。硬要启用会出事：关门分支的条件是 boxes[n].state == ST_OPEN && !doorOpenOf(n)，一旦进了 ST_ERROR 就再也匹配不上， 状态会永久卡死，只能重启。

⚠️ 四格里只有 1 号格跑得到「门真的被打开了吗」这一步。

  • 1 号格有真簧片，doorSeenOpen 防呆照常 —— 没见过门开就不认门关（这是坑 11 的修法）。
  • 2~4 号格没有硬件可读，doOpen() 走另一条分支：设一个 closeAt = now + 3s，到点自己发 door_opened 再发 door_closed， 格内有无按动作直接置位（存 = 有 / 取 = 无）。 报文格式与真机完全一致，后端一行都没改。
下面「上电初态」那条同理只对 1 号格有意义（它有秤可读），虚拟格一律从 IDLE / 无物 起步。

上电初态不是固定的：固件读一次压力传感器，按实况落到 IDLE 或 OCCUPIED， 避免断电恢复后状态错乱。 ⚠️ 但这也意味着零点就是在开机那一下取的 —— 托盘上放着东西时重启，那东西会被当成零点，之后一直报「空」。 补救是把托盘清空重启，或者在串口里敲 t 重新去皮。

图 5　订单状态机（后端）

落库在 orders 表。这是「防执行失败」的落点 —— 命令发出去了不算成功，门磁回执才算。

为什么 done 要等门磁回执：后端不因为「命令发出去了」就认为存取成功 —— 设备可能根本没开门，或者开了没人关门。pending 15 秒、opened 60 秒是两个兜底超时 （可用环境变量 OPEN_ACK_TIMEOUT / OPEN_CLOSE_TIMEOUT 调），超时一律判 failed。

⚠️ 已知缺口：advance() 是「按格」推进的，不是「按单」。 它先从这一格里挑单、再做条件 UPDATE： SELECT id FROM orders WHERE box=? AND status=? ORDER BY id DESC LIMIT 1 然后 UPDATE … WHERE id=? AND status=? —— 「推进哪一张」是按格号挑的，因为门磁回执里没有订单号。 于是这个时序会出事：某格上一单的 door_closed 迟到，而该格此刻恰有另一张 在 opened 的单，这张回执就会推错单（还会用错的 closed_at 去计费）。 现实中要凑齐这个时序不容易，但它是真的。 根因与修法：publish_open() 下发的 cmd 里其实带着 order， 但固件没把它带回回执 —— 让固件原样回传、advance() 改成按 id 推进即可。 本次没做，只记在 README 的「已知缺口」里。
