# 校园智能寄存柜 —— 物联网课程设计原型

ESP32 + MFRC522 + SG90 + 门磁 + HX711 压力传感器，通过 MQTT 与 Flask 后端通信，
用户用**微信扫一扫**柜体二维码打开 H5 页面开柜，也可**刷校园卡**直接开门。

柜子做的是 **4 格**，但**真机只装了 1 号格的硬件**（舵机 / 门磁 / 压力传感器各一套，
GPIO 也就只够一格）。2~4 号格由固件**虚拟**出来：状态、开门时序都自己演，
后端把它们当成真的在线柜格。所以监控台上看到 2~4 号格**显示离线是正常的**，
不是页面坏了 —— 见下面「多格：一格真硬件 + 三格虚拟」。

```
手机(微信扫一扫) ──HTTP──> Flask 后端 ──MQTT──> Mosquitto ──MQTT──> ESP32
ESP32 ──MQTT(status/event/card_scan)──> Mosquitto ──MQTT──> Flask 后端 ──HTTP──> 监控台
```

| 路径 | 说明 |

| 器件 | 引脚 | 备注 |

| MFRC522 SCK | GPIO 18 | |
| MFRC522 MISO | GPIO 19 | |
| MFRC522 MOSI | GPIO 23 | |
| MFRC522 SS/SDA | GPIO 21 | 避开 GPIO5 这个 strapping 脚 |

| MFRC522 VCC | **3.3V** | ⚠️ 接 5V 会烧模块 |

| 磁性门控开关 | GPIO 4 | 另一端接 GND，代码用内部上拉；极性见坑 11 |
| HX711 DT | GPIO 27 | 压力传感器数据（输入），代码用内部上拉；**建议串 1kΩ 电阻**，见坑 12 |
| HX711 SCK | GPIO 32 | 压力传感器时钟（输出） |
| HX711 VCC | **3.3V** | ⚠️ **接 5V 实测会整块板子报废**（不是只烧一个脚），见坑 12 |
| OLED SCL | GPIO 26 | 0.96" SSD1306，I2C 四针，VCC 接 3.3V |
| OLED SDA | GPIO 25 | |

这张表是**整个柜子**的接线，但里面有两类器件，多格之后区别很关键：

| 类别 | 器件 | 一格一份？ | 后果 |
|---|---|---|---|
| **柜体级** | ESP32、RC522、OLED | ❌ 全柜共用 | 读卡器**不知道**你站在哪一格前，屏幕也只能轮流显示各格状态 |
| **柜格级** | SG90、门磁、HX711 | ✅ 每格一套 | 只装了 1 号格；2~4 号格没有任何硬件，由固件虚拟 |

**12 个可用 GPIO 只够一格的柜格级器件**（舵机 + 门磁 + HX711 是 4 根线，四格要 16 根，
而这个板子伸出排针的脚本来就不多，再凑就得动 strapping 脚）。所以是 1 真 + 3 虚，
不是"没配好"。

### 上电前的接线核对（每次改线都念一遍）

> 2026-10-12：HX711 的 VCC 插到了 5V，**整块板子报废**（见坑 12）。
> **2026-10-16：新板子换上，整套固件真机验通** —— WiFi / MQTT / 刷卡 / 舵机 / OLED / HX711
> 一项不落，存件和取件两条闭环都当场走过。**现在在用的就是这块。**
> 下面这套动作两分钟，能挡住这一类错误 —— 主要是**顺序**，不是接线知识。

**① 拔掉 USB。** 所有接线在断电状态下做，插拔过程中不要带电。

**② 先只接电源线，不接信号线。** 先接 VCC / GND，**上电，量一下电压，确认无误后
再断电去接信号线**。今天烧板子的关键就在这里：5V 之所以能打进 ESP32，
是因为**那根 DT 信号线当时已经接着了**。只要信号线是最后接的，
就算 VCC 插错，上电时也伤不到 ESP32。

**③ 谁吃 3.3V —— 这三个模块的 VCC 一个都不能插到 5V。**

| 模块 | VCC | 插错的后果 |
|---|---|---|
| MFRC522 | **3.3V** | 模块直接报废（坑 2） |
| HX711 | **3.3V** | **整块 ESP32 报废**（坑 12） |
| OLED | **3.3V** | 报废 |

⚠️ 30-pin 板上 **`3V3` 和 `5V`(VIN) 是挨着的**。插之前用指甲按住 `3V3` 那一列再插，
别凭手感。

**④ 唯一接 5V 的是舵机**，而且建议单独供电、只和主板共地（坑 3）。

**⑤ 共地。** 所有模块的 GND 都要回到主板 GND —— 包括单独供电的舵机，
否则信号没有参考电平。

**⑥ 门磁的两端是 `GPIO 4` 和 `GND`**，不是 3.3V。（它的另一端接 GND 才算"门关"。）

**⑦ 信号线最后接，接完再上电。** 上电后 30 秒内应该看到：
板载电源灯亮 → 电脑多出一个 COM 口 → 串口打印 `[scale] 去皮完成`。

**如果插上后电脑连 COM 口都不出现**，立刻拔掉，别再插第二次 ——
那是供电段已经出事的信号，判断方法见坑 12。

不需要手动跑，除非你想看实时日志：

```bash
"C:\Program Files\Mosquitto\mosquitto.exe" -c "C:\Program Files\Mosquitto\mosquitto.conf" -v
# 注意：服务已经在跑并占着 1883，要先 net stop mosquitto（需管理员）
```

自查（另开一个终端）：

```bash
cd "C:\Program Files\Mosquitto"
.\mosquitto_pub.exe -h 127.0.0.1 -u locker -P locker123 -t locker/selftest -m hi  # 应该成功
.\mosquitto_pub.exe -h 127.0.0.1 -t locker/selftest -m hi                         # 应该 not authorised
```

要改账号密码，用管理员 PowerShell 重跑 `fix-broker.ps1`（它把四件事都做了：建账号、
**给服务账户授权读密码文件**、写配置、重启服务），然后同步 `backend/app.py` 的
`MQTT_USER`/`MQTT_PASS` 和 `firmware/campus_locker.ino` 顶部。

> ⚠️ **一个坑了很久的坑，写在这里免得再踩**：
> `mosquitto_passwd.exe` 建出来的密码文件，ACL **只给了运行它的那个用户**（连 SYSTEM、
> Administrators 都没有）。而 Windows 服务是以 **LocalSystem** 身份跑的，读不到这个文件，
> 于是 mosquitto 启动后**立刻干净退出**：`net start` 报"启动成功"，但 1 秒后服务就 Stopped、
> 1883 无人监听、日志看起来一个字都没写（因为日志文件本身也是 SYSTEM-only 的 ACL，
> 用普通账户甚至管理员都打不开）。真正的报错只有这一行：
>
> ```
> password-file: Error: Unable to open pwfile "C:\Program Files\Mosquitto\passwd".
> ```
>
> 解法就是一行：`icacls "C:\Program Files\Mosquitto\passwd" /grant *S-1-5-18:(R)`
> （`S-1-5-18` 即 `NT AUTHORITY\SYSTEM`）。`fix-broker.ps1` 里已经包含这一步。

#### 环境准备（只需做一次，本机已装好）

开发板核心 **`esp32` by Espressif `3.3.10-cn`**，来源是官方给出的国内镜像：

```
首选文件 → 首选项 → 附加开发板管理器网址：
https://jihulab.com/esp-mirror/espressif/arduino-esp32/-/raw/gh-pages/package_esp32_index_cn.json
```

> ⚠️ **必须选带 `-cn` 后缀的版本**。Arduino 官方索引里也有 `esp32`（3.3.11 / 3.3.12），
> 但那些包的下载地址指向 **github.com**，实测只有 90 KB/s 左右；`-cn` 包走
> `dl.espressif.cn`，实测 3.5–5.7 MB/s，快 40 倍以上。装完体积约 6 GB（解压后）。

依赖库（**工具 → 管理库** 里搜着装）：`PubSubClient`、`ArduinoJson`（7.x）、`MFRC522`、`ESP32Servo`、`U8g2`（2.36+）。

> ⚠️ 是 `ESP32Servo` 不是 `Servo`。esp32 core 2.x 自带 `Servo` 库，**3.x 已经移除了**，
> 直接用 `#include <Servo.h>` 会报 `fatal error: Servo.h: No such file or directory`。
> ESP32Servo 的头文件是 `ESP32Servo.h`，但类名仍叫 `Servo`，其余代码不用改。

装完在 **工具 → 开发板** 选 `ESP32 Dev Module`，插上板子选对应 COM 口即可编译上传。

**有真板子时不需要这一段** —— 板子自己就是那台"柜子"，上电即可，而且多验一条模拟器
验不了的东西：**舵机开锁 ≠ 门被打开**（见坑 11）。

没硬件时才用模拟器顶替设备那一层。**常驻的那个才是"柜子"**，刷卡是另一条命令、在另一个终端敲：

```bash
# 终端 A：常驻，假扮整个柜子（默认 4 格），等后端下发开门命令
.venv\Scripts\python.exe device_sim.py

# 终端 B：刷一次卡（跑完就退）
.venv\Scripts\python.exe device_sim.py --card 04A12B3C4D
```

> **一个进程假扮的是整个柜子，不是一格**：一台 ESP32 上跑一块固件，心跳和事件里都带格号，
> 一个进程就报 N 格。`--boxes` 要和后端的 `BOX_COUNT` 一致（**两边默认都是 4**）：
>
> ```bash
> .venv\Scripts\python.exe device_sim.py --boxes 4   # 默认就是 4，写出来是为了对齐后端的 BOX_COUNT
> ```
>
> 想退回单格：后端 `set BOX_COUNT=1`，模拟器 `--boxes 1`。

> `--card` 是**纯注入器**：只往 MQTT 发一条 `card_scan`，不订阅 `cmd`、不扮演柜子。
> 真开门的是终端 A 那个常驻进程（或真机）—— 刷卡本来就得有读卡器在场。
> 早先的版本让 `--card` 也订阅 `cmd`，于是两个进程抢着开门，**每个回执都重复一遍**
> （日志里会多出"迟到回执"），已改掉。
> 这条报文里**不带格号**：RC522 是全柜公用的，它读到的只是一张卡 —— "刷哪一格"由后端算。

演示失败路径用这两个开关，对应后端的两个超时：

```bash
.venv\Scripts\python.exe device_sim.py --drop-open   # 收到命令但不回 door_opened → 15s 后判 failed
.venv\Scripts\python.exe device_sim.py --stuck-open  # 开了就不关 → 30s 报 door_left_open → 判 failed
.venv\Scripts\python.exe device_sim.py --door-hold 5 # 开门后 5 秒关门（默认 3 秒）
```

## 注册与绑卡

存件要求手机号**已在 `users` 表里**，所以新用户得先注册。扫码页是**一页一件事**的：
首页只有 存件 / 取件 / 我的，绑卡和注册各是独立的一页，从「我的」页进去。

1. **「还没注册？点这里注册」** —— 填姓名 + 手机号 → 注册。手机号有 UNIQUE 约束，
   重复注册会返回 409。注册完自动回到「我的」页。
2. **「绑定校园卡」** —— 点「绑定校园卡」后，**45 秒内刷一次卡**，那张卡就绑到当前手机号
   （当前手机号 = 页面上填的那个，存件页 / 我的页 / 绑卡页三个输入框是同一个值）。

手机号未注册就存件，后端回 `403`；页面会**直接把人送到注册页**并把手机号填好
（以前只弹一句话，新用户在那儿是个死胡同）。取件的 `403`（取件码不对）不跳页 —— 那是没得救的。

绑卡为什么要点一下才刷？因为**后端收到 `card_scan` 时并不知道这张卡属于谁** —— 刷卡报文里
只有一个 UID，没有登录态。所以必须由页面先认领手机号（`bind_wait` 记一个 45 秒的窗口），
用户再刷卡，两边才配得上。窗口是**一次性的**：配完一张卡就作废，紧接着刷的第二张不会被误绑。

反过来说，**已经绑给别人的卡偷不走** —— 那种卡在查表时就能查到主人，走的是正常授权分支，
根本进不了绑卡那段。

换卡（解绑旧卡再绑新卡）课设不做入口，要换直接改库：

```bash
.venv\Scripts\python.exe -c "import sqlite3; c=sqlite3.connect('locker.db'); c.execute('UPDATE users SET card_uid=NULL WHERE phone=?',('13700137000',)); c.commit()"
```

## 状态机

**柜格状态**（设备端，固件上报）——**每一格各自一套**：

```
IDLE(锁闭·无物) --存件--> OPEN --关门且压力传感器测到物品--> OCCUPIED(锁闭·有物)
OCCUPIED --取件--> OPEN --关门且压力传感器测到空--> IDLE
OPEN 超过 30s 未关 --> 上报 error(door_left_open)
```

⚠️ **关门回执之前，门必须真的被打开过**（固件里的 `doorSeenOpen`）。**舵机开锁 ≠ 门被打开**：
下单时若门正好关着，`doOpen` 置 `ST_OPEN` 后下一圈（50 ms）就会把它当成关门回执，
订单 1 秒就 `done`，而东西还没放进去 —— 那一刻压力传感器读到无物，状态还会落成 `IDLE`，
于是柜里明明有东西、状态却说空，紧接着的取件被 `nothing_to_pickup` 拒掉。
真机流程必须是 **下单 → 舵机开锁 → 手动拉开门 → 放东西 → 关门**。

⚠️ **读到"门关着"之后不立刻上锁，先等 400ms 再确认一次**（`DOOR_SETTLE_MS`）。
簧片是**渐近吸合**的 —— 磁铁离到位还差几毫米，触点就已经闭合了，而门靠惯性还要再摆最后一小段；
越过吸合距离那一下触点自己还会抖几十毫秒。`loop()` 是 50ms 一圈、**一次采样定生死**，
正好能抽中抖动间隙读到"关"。上锁太早 = **锁舌顶在一个还在走的门上**，装上真锁体就是卡死或堵转
（SG90 堵转约 700mA，够把板子拉重启）。等完**再确认一次**才是治抖动的地方：又弹开了就当没发生，
下一圈重新计。这块用阻塞 `delay`，和 `setLock()` 里那个 `delay(400)` 同一套路数 ——
最坏影响是 MQTT 和心跳晚几百毫秒，而心跳 10s、门开报警 30s，余量极大。
本机**没有柜体、舵机空转**，所以这个竞态**现在露不出来**，属于"装柜体前必须补、补了也暂时验不了"的一环。

**虚拟格演的是同一个状态机，只是没有硬件可读**：`doOpen()` 里走另一条分支 ——
不做 `doorSeenOpen` 防呆（没有簧片可读），而是设一个 `closeAt = now + 3s`，
到点自己发 `door_opened` 再发 `door_closed`，格内物品按动作（存=true / 取=false）直接置位。
所以 2~4 号格跑出来的报文和真机**格式完全一样**，后端一行都不用改。

**订单状态**（后端，落库在 `orders` 表）：

```
pending(已下发开门命令) --door_opened--> opened(门确实开了) --door_closed--> done(门关了，落库)
   |                                        |
   +-- 15s 没等到 door_opened ---------------+-- 60s 没等到 door_closed --> failed
```

关键点：**`done` 必须等到门磁回执**。后端不因为"命令发出去了"就认为存/取成功——
设备可能根本没开门、或者开了没人关门。`pending` 超时 15s、`opened` 超时 60s
（都可用环境变量 `OPEN_ACK_TIMEOUT` / `OPEN_CLOSE_TIMEOUT` 调），超时判 `failed`。

⚠️ **但"门关了"也不等于"操作成功"—— 成败只有秤知道。** 所以固件的 `door_closed`
回执里**多带一个 `state`**（固件按秤算出来的结论，`OCCUPIED` / `IDLE`），
后端据此落 `done` 还是 `failed`（判据在 `door_close_verdict()`）：

| 回执里的 `state` | 订单是 | 后端落到 |
|---|---|---|
| `OCCUPIED` | 存件 | `done`，发取件码 |
| `IDLE` | 存件 | **`failed`** ——「门关了但秤报格内为空，东西没放进去」 |
| `IDLE` | 取件 | `done`，正常结算 |
| `OCCUPIED` | 取件 | **`failed`** ——「门关了但秤报格内还有东西，东西没拿走」 |

发的是 `state` 而不是裸的 `item`：这样后端直接复用**固件自己的判据**，两边只有一个口径。
**模拟器也带这个字段**（`device_sim.py` 早就算好了 `state`，只是原来没往报文里塞），
所以走兜底方案演示时这条判定照样生效。真正不带它的只有**老固件** —— 那种情况退回
老行为"门关了就算成功"，报文向后兼容。

没有这一条的话，"开了门又关上、但什么都没放"会被记成一次**成功的存件**、还发一个取件码出去，
而格子里其实是空的 —— 用户拿着码来取取不到，格子还会卡死。

> ⚠️ **失败的存件单上照样带着取件码** —— 码是"开门那一刻"生成并发给页面的（用户得马上看到），
> 不是门关了才生成。所以一次失败的存件会让用户看到一个码，但那一单是 `failed`，
> `occupant()` 不认它，**拿这个码取不到任何东西**（实测回 409「柜格里没有东西」）。
> 扫码页盯着自己那一单，失败会当场改口提示重试 —— 所以顺序是"先看到码、几秒后被告知没成"。

### 真机格对账（DB 和秤分家了怎么办）

上面那条是**从源头不产生分歧**。但分歧还是会产生，所以后端还有一层兜底：
拿秤的读数和 DB 里的占用记录对账，**连续矛盾够久就把那条脏的记录判失败**
（`check_reconcile()` / `drop_ghost_order()`）。

两个方向，处理方式不一样：

| 情况 | 含义 | 处理 |
|---|---|---|
| DB 有存件单在占着，秤连续 30s 报**无物** | 那条存件单是**假的** | 自动置 `failed`，柜格当场解锁，写审计 |
| 秤连续 30s 报**有物**，DB 里没有任何单 | 有东西进柜**没记上账** | 只报警（写审计），**不自动动数据** |

**为什么会走到这一步：** 后端的 `occupant()` 只认 `orders` 表，设备的 `state` 只活在内存里。
两边一分家就**互相堵死** —— 后端说"格里还有东西"不让存、固件说"这格是空的"不让取
（`nothing_to_pickup`），谁也解不开，**只能人去改库**。2026-10-16 真机就是这么卡住的：

```
后端: occupant(1) = 订单 112（一条 4 秒就关门的存件单，被标成 done）
固件: boxes[1].state = IDLE（秤说托盘是空的）
-> 扫总码存件：被 pick_free_box 跳过，存进 2 号格
-> 扫 1 号格码存件：后端拦「柜格里还有东西，请先取走」
-> 取件：固件拦 nothing_to_pickup，柜门根本不开
```

几个必须守住的写法：

- **只在真机格上做**（`REAL_BOX`，默认 1）。2 号及以后的 `item` 是固件按后端指令自己编的，
  拿它对账等于自己骗自己。
- **用"连续矛盾多久"而不是"矛盾多少次"**（`RECONCILE_AFTER`，默认 30s）。
  门关那一下读数会跳，短时间内的几次心跳可能都撞在这个窗口里，按次数算会**误杀一张好单**。
- **正在操作的那一格不许动**（`active_order()` 非空就跳过），免得把进行中的单判死。
- **设备掉线时不许动** —— 读数都不刷新了，不能拿旧读数判案。
- 对账挂在**状态报文**上，而且必须在 `boxes_lock` **之外**调：
  `device_online()` 要拿这把锁、`occupant()` 要开 DB 连接，持着锁再去做这两件事会把锁序搞乱。
- `UPDATE` 在 `tx()` 里，`audit()` 必须在 `tx()` **之外** —— `audit()` 会另开一条连接，
  握着写锁再调它就是自己等自己（同 `settle_pickup` 的注意事项）。
- **对账只改得了 DB，改不了固件内存里的 `state`。** 格子没开关门，固件不会自己更新。
  所以固件那两条"满柜存件 / 空柜取件"的防呆**必须读秤（`itemPresent()`），不能信缓存的 `state`**。
  ⚠️ 这是 2026-10-22 真机撞出来的：旧写法在对账把柜格解开之后，下一次存件仍然被固件
  挡成 `already_occupied` —— 用户看到的是"格子明明解开了却存不进去，只能重启板子"。
  改成读秤后，同一个状态（`state=OCCUPIED` 但 `item=False`）下发存件，门正常开。

> 附带一个**正常但容易吓人**的现象：对账把脏单判失败之后，监控台上那一格会显示
> `状态 = 有物`、`格内 = 无物`，两边不一致。这是固件的缓存状态还没被下一次关门店正 ——
> **不是新 bug**，下一次开门关门就自己对齐了，期间存件、取件都正常。

另一处细节：命令**先落库再 publish**。设备最快毫秒级就回 `door_opened`，
如果那时订单还没写进去，事件线程就不知道这条回执是谁的。

#### 板子不在手上时，怎么验这两层

这两层都只活在后端（`door_close_verdict()` / `check_reconcile()`），
所以**不用真机也能验**：写个小脚本假扮设备，收到开门命令就回
`door_opened` + `door_closed`（**带 `state`**，`state` 由脚本说了算 —— 想造"假成功"就故意报反）。
关键是**别碰到现场那台**，三处都要改：

| 要改的 | 改成 | 不改会怎样 |
|---|---|---|
| `app.py` 的 `DEVICE_ID` | 别的（如 `verifydev`） | 你的假设备报文会被**现场那台后端**一起收下，污染真库 |
| `app.py` 的 `HTTP_PORT` | 别的（如 `5055`） | 端口撞车起不来 |
| `app.py` 的 MQTT `client_id` | 别的 | **同名会把现场那台后端从 broker 上顶掉** —— 它不发心跳，四格全变离线 |

`DB_PATH` 是 `Path(__file__).with_name("locker.db")`，所以把改过的 `app.py` 复制到一个
空目录里跑，它自己在那儿建一个**干净的库**，和真库天然隔离。
`RECONCILE_AFTER` 调小（比如 3）就不用等 30 秒。
2026-10-16 用这套验过 25 项：正常存/取各一轮、①「存空」「取件没拿走」各判 `failed`
且柜格不卡死、③ 两个方向都按预期处理 —— **全绿**。

> ⚠️ **它只证明后端逻辑，证明不了固件。** 假设备没有"内存里缓存一个过期的 `state`"
> 这回事 —— 2026-10-22 正是上真机（真 HX711 + 真门磁）才撞出上面那条
> "DB 解开了、固件还以为满"的洞。**涉及固件行为的改动，最后必须上真机走一遍。**
> 真机上验这一套的做法：存件 → 不碰门把东西拿走 → 等 30 秒看对账触发 → 再发一张存件单，
> 看固件是开门还是回 `already_occupied`。

## 多格：一格真硬件 + 三格虚拟

**硬件只能供一格**：舵机 + 门磁 + HX711 是 4 根线，四格就是 16 根，这块板子伸出来的
可用脚不够（详见「接线」那节）。所以 1 号格是真家伙，2~4 号格由固件虚拟 ——
但**对后端来说它们是平等的四格**，报文格式、状态机、自动分配全都不用区分。

| | 1 号格 | 2~4 号格 |
|---|---|---|
| 舵机 / 门磁 / HX711 | ✅ 真实 | ❌ 没有 |
| 开门 | 舵机转 → **人手动拉门** → 簧片读到 → 发 `door_opened` | 内部计时 3 秒后**自己发** `door_opened`、再发 `door_closed` |
| 格内有无物品 | `itemPresent()` 读 HX711 | 按动作直接置位（存=true / 取=false） |
| 关门防呆 `doorSeenOpen` | ✅ 有（真簧片才暴露的坑，见坑 11） | ❌ 不适用，没有簧片可读 |
| `door_closed` 报文体 | 多带一个 `state` 字段 = 秤判出来的结论 | 同左（按动作置位后的结论） |
| OLED / RC522 | **柜体级**，全柜共用这一套 | 同左 |

**`state` 是干嘛的**：门关了只说明"门关了"，不说明"存件成功" —— 存件时门关了但秤报空、
取件时门关了但秤还报有物，都是动作没真做成。所以固件在关门回执里把自己判出的
`OCCUPIED`/`IDLE` 一并发上来，后端拿它和订单动作对一下（见「真机格对账」那节上面的四种组合）。
**虚拟格也发这个字段**，所以后端这条判定对四格是同一套代码，不用区分。

**没有硬件时用模拟器**：`device_sim.py` 一个进程假扮整个柜子（默认 4 格），
上面这些行为它都演（见「设备端」那节）。

**柜格数配置**：后端 `BOX_COUNT`（默认 4）和固件的 `#define BOX_COUNT`（默认 4）**必须一致**，
模拟器用 `--boxes` 对齐。两边不一致的症状是：后端挑了一格，设备回一句"格号不对"然后丢掉 ——
订单挂在那儿等超时。

### 存件时怎么挑格：`pick_free_box()`

扫**柜体总码**存件时页面上没有格号，格由后端挑。规则很简单：

1. **只看在线的格**。不在线的格东西放不进去，挑了也是白挑。
2. 在在线的格里取**格号最小**的空格。

"空格"用 `occupant(c, n) is None` 判定 —— 这是全项目**唯一**一个"这格里有没有东西"的口径
（见下面 ⚠️）。四格都在线且都空时，第一单落 1 号格；1 号格被占了，下一单落 2 号格。

⚠️ **`occupant()` 是唯一的权威口径，绝不能再写第二个。** 它返回某格最后一个
`done` 的 `store` 单 —— **必须是 `action='store'`**：取件单有时候也被 `door_closed`
推进成 `done`，只按"最后一个 done"来算的话，取完件的格会被判成"有东西"。
挑空格、凭码找格、刷卡定格、取件前校验、看板统计**全都调它**，
就是怕哪天有人图省事写个 `SELECT ... FROM orders WHERE box=?` —— 那就是第二个口径了。

⚠️ **在线快照必须在开事务之前取**。`device_online()` 要拿 `boxes_lock`，
而 `create_order()` 在事务里握着 DB 写锁 —— 持写锁再等进程锁是**锁序倒置**，
并发下会死锁。所以是"先算在线集合，再带着它进事务"。

### 柜体总码 vs 柜格贴

两种码，贴的位置和行为都不同：

| | 柜体总码 | 柜格贴 |
|---|---|---|
| 张数 | 1 张，贴柜子正面 | 每格 1 张，贴在各自门上 |
| URL | `/scan` | `/scan?box=N` |
| 存件 | **后端自动挑格**（`pick_free_box`） | 就存进这一格 |
| 取件 | **凭码自己找格**（`box_of_code`） | 码必须属于这一格，否则 409 |
| 页面 | 存完会回显"已放入 N 号柜格，取件码 xxxx" | 从头到尾显示固定的格号 |

用户视角：**总码更好用**——存件不用挑格，取件不用记格，记个码就行。
柜格贴是给"我就想放这一格"的场景，顺带也说明柜子有几格。

`box_of_code()` 也是**遍历所有格去调 `occupant()`**，而不是直接
`SELECT box FROM orders WHERE pickup_code=?`。直接查的话，一个早就取走的存件单还会命中，
于是给用户开一次空柜门 —— 宁可多查几次，也不要第二个口径。

### 刷卡怎么知道是哪一格

**RC522 是柜体级的，它读到的只是一张卡，卡不会说"我在 3 号格前"。**
所以"刷哪一格"是**后端按卡主算出来的**：

- 这张卡的主人**占着哪一格** → 就是取件，开那一格。
- 哪一格都没占 → 就是存件，格从在线的空格里挑（和扫总码**完全走同一条路**）。

顺带一个好处：早先那条"卡主不是这格占用者"的拒绝分支**整条消失了** ——
格是按卡主自己算出来的，算出来的格不可能是别人占着的。（设备侧对应地把
`not_owner` 的翻译也删了。）

**卡还没绑** → 走原来那条绑卡流程（页面先点「绑定校园卡」，45 秒内刷的那张绑给它）。
**欠费** → 拒绝存件（`reason: balance`）；**一台设备都没在线** → 拒绝（`device_offline`）；
**满柜** → 拒绝（`reason: full`）。

⚠️ 这里有个刻意的顺序：存件前先在事务外**预检一次"还有没有空格"**。
不然会出现"屏幕说『已授权，请放入物品』，然后门一声不响" ——
屏幕上那句谎话比多查一次库难看得多。

### ⚠️ `advance()` 是「按格」推进的，不是「按单」

`advance(box, OPENED, DONE)` 确实是条件 UPDATE（CAS，靠 `rowcount` 守卫），
但它**先从这一格里挑单，再 CAS**：

```sql
SELECT id FROM orders WHERE box=? AND status=? ORDER BY id DESC LIMIT 1   -- 挑"这一格最新的那张"
UPDATE orders SET status=? WHERE id=? AND status=?                        -- 再 CAS 推它
```

也就是**"推进哪一张"是按格号挑的，报文里没有订单号**。于是这个时序会出事：
1 号格上一单的 `door_closed` 迟到，而 1 号格此刻恰好有**另一张**在 `opened` 的单 ——
那张回执就把**另一张单**推成了 `done`（顺手用错的 `closed_at` 去计费）。

现实中要凑齐这个时序不容易（同一格得在上一单没关干净时就开了下一单），但它是真的。
根因是**回执里没有订单号**：`publish_open()` 下发的 `cmd` 里其实带着 `order`，
但**固件没有把它带回 `door_opened` / `door_closed`**，只回了格号。修法是固件原样回传
`order`、`advance()` 改成按 `id` 推进。**这次没改**，记在「已知缺口」里。

根因是**回执里没有订单号**：设备侧 `cmd` 报文里其实带着 `order`（见 `publish_open`），
但**固件没有把它带回 `door_opened` / `door_closed`**，只回了格号。修法就是让固件把
`order` 原样回传、`advance()` 改成按 `id` 推进。**这次没改**，记在「已知缺口」里。

## 物品检测（HX711 压力传感器）

柜格底部放压力传感器，**只回答"有没有东西"，不称重**——所以不上报克数、屏幕上也只有"物有/物无"。
换成压力传感器之前用的是光电，功能一样，`itemPresent()` 的签名和 4 个调用点一行没改。

**判定方式：把读数减去零点，超过门限就算有物。**

应变片的读数只有相对意义、**没有绝对零点**，所以必须先定一个基准。零点 = 开机时托盘的读数
（去皮）。既然只要"有/无"，基准 + 一个计数门限就够了，**不需要标定系数**——
网上例程里的 `GapValue 430`（计数/克）是那个秤在那个供电电压下标出来的，
换传感器、或者激励电压从 5V 变 3.3V 就对不上了。门限是 `ITEM_THRESHOLD_COUNTS`，
默认 8000 计数（按 430 计数/克粗算是 20 克上下），**按串口实测调**。

**2026-10-16 真机实测**（读串口那行 1 Hz 的原始计数，托盘空载时开机去皮）：

| 状态 | 与零点之差（计数） | 波动 |
|---|---|---|
| 空载（去皮后） | ≈ 0 | ±62 |
| 放一本书 | **−22,780** | ±33 |
| 拿走 5 秒后 | ≈ −40 | ±30 |

信噪比约 **367:1**，三种状态隔得干干净净，**门限 8000 待在中间不用动**
（离噪声 130 倍，离信号 2.85 倍）。承重时读数**很稳**，25 秒里只漂 ±33。

⚠️ **但这个传感器的静息点很偏**：零点读出来是 **−8,253,385**，而 HX711 的 24 位满量程是
±8,388,607 —— 静息点压在**负满量程的 98.4%** 上，往负方向只剩约 **13.5 万计数**的余量。
载荷又恰好让读数**往负方向**走，于是**载重上限大约是那本书的 6 倍**，再沉就撞满量程。
撞了不会误判（`fabsf` 照样判"有物"），但余量就这么大，换更重的演示物之前先看一眼串口。

健康的应变片零度误差该在一万计数上下，**−825 万这个落点不正常**，大概率是载荷传感器四线
**配对错了**（A+/A− 和 E+/E− 不是同一对对角线）。本次**没查**，因为开机去皮把这个绝对偏移
整个减掉了，功能上不受影响。**哪天行为变怪，先查这四根线的配对** —— 万用表两两量六种组合：
**两个约 1000Ω 的是一对对角线，四个约 750Ω 的是跨臂**，配对一眼就出来了。

⚠️ **零点是在开机那一下取的，所以托盘上放着东西时重启，那东西会被当成零点**，之后一直报"空"。
补救：把托盘清空重启，或者**在串口里敲 `t` 重新去皮**。
开机时若读不到模块，屏幕会弹一条"称重模块 没读数，检查接线"。

⚠️ **模块 VCC 必须接 3.3V，接 5V 会整块板子报废（实测，见坑 12）。**
常见的那种红色小板把 DVDD 和 VCC 短在一起：接 5V 时 DT 会输出 5V 打进 ESP32（绝对最大才 ~3.6V），
同时 3.3V 的 SCK 又够不到 5V 供电下的高电平门限，两头不讨好。

固件里那份驱动是从网上常见的清翔 51 例程改的，**有三处照搬会出事**（都在
`campus_locker.ino` 的「HX711 压力传感器」一节里写了原因）：换掉例程的 GPIO 2/3（strapping + 串口 RX）、
给等待就绪加上超时（例程是死等，模块掉线整块板子卡死）、**全程用有符号数**
（例程用 `unsigned long` 算差值，读数掉到零点以下会回绕成 42 亿恒大于阈值，柜子从此永远认为"有物"）。
24 位读数的第 25 个时钟脉冲（选下一轮通道增益）和 `^= 0x800000`（偏移二进制转补码）**不能省**。

## 屏幕（0.96" OLED）

柜体上挂一块 SSD1306，128×64，I2C 四针，走 `GPIO 25(SDA) / 26(SCL)`。

**常驻页面在四格之间轮放**（`OLED_ROTATE_MS = 2000`）：柜格号 + `1/4` 页码、
在线/断网、状态（空闲/门已开/有物品）、门·物·锁三个传感器读数。
多格之后屏幕只有一块，只能轮流看 —— **没有 toast 的时候才翻页**，
不然刷卡反馈会被翻页冲掉。
**刷卡和开门时插播一条反馈**（此时锁定在被点到的那一格），到点自动退回轮放：

| 触发 | 屏幕显示 |
|---|---|
| 刷卡 | 卡号 + `验证中…` |
| 后端回 `ok`（正常授权） | `已授权 / 请放入物品并关门` |
| 后端回 `ok` + `card_bound` | `绑卡成功` |
| 后端回 `deny` + `not_bound` | `此卡未绑定 / 请先在手机页面绑卡` |
| 后端回 `deny` + `device_offline` | `设备离线` |
| 后端回 `deny` + `balance` | `余额不足 / 请先充值` |
| 后端回 `deny` + `full` | `柜子满了 / 请稍后再试` |
| 下发开门命令 | `N 号柜格` + `存件`/`取件` + `柜门已开，请关门` |
| 关门 | `存件完成`/`取件完成` |
| 开柜前防呆拒绝 | `无法开门 / 这格已经有东西了`（或"这格是空的"） |

`auth_result` 的 reason 一共四种（`not_bound` / `device_offline` / `balance` / `full`），
**在固件里逐个翻成人话再上屏** —— 屏幕是给站在柜子前面的人看的，显示 `not_bound` 等于没显示。

> 早先有个 `not_owner`（"不是你的物品"）：那时刷卡报文里带着格号，后端只能去比"卡主是不是
> 这格的占用者"。现在**格是按卡主自己算出来的**（见下面「刷卡怎么知道是哪一格」），
> 算出来的格不可能是别人占的，这条分支就再也走不到了，已删掉。

### ⚠️ 屏幕显示不了取件码

设备**不知道取件码**。码是后端在存件时生成的，只回给了扫码页，**从来没下发给设备**。
所以屏幕上只能显示柜格状态和刷卡结果。要在柜体屏幕上显示取件码，得改后端协议
（让 `/api/open` 之后把码发给设备），**本次没做**。

### 两条实测出来的注意

1. **中文字库吃 flash，但吃得下**。`u8g2_font_wqy12_t_gb2312` 一个字体数组 **197.9 KB**
   （在 U8g2 那个 38.8 MB 的 `u8g2_fonts.c` 里，链接器只挑用到的那个）。加之前固件
   943 KB / 71%，加完 **1178 KB / 89%**。四格 + 轮放代码又涨了一点，
   目前 **1180347 字节 / 90%**，还剩约 127 KB。想再省就把屏上文案改成英文，或换更小的字库。
2. **别把 SDA/SCL 接到 GPIO 34/35/36/39**。那几个是**只读输入脚**，I2C 要双向，
   接上去屏幕全黑 —— 现象是"我明明什么都没接错"。25/26 是干净的选择。
   另外 U8g2 这里用的是**软件 I2C**（`_SW_` 而不是 `_HW_`），不挑脚、不依赖外设映射，
   换引脚不用改配置，代价是全屏刷新几十毫秒 —— 对状态屏完全够用。

| GET | `/api/logs` | 最近 50 条操作日志（**要口令**） |

（只能存件时遇到）、`403` 未注册手机号 / 取件码不对、`409` 柜格占用状态不符或该格有操作
正在进行、`503` 设备离线。

⚠️ **`box` 非法一律报错，绝不静默回落到 1 号格。** 这是多格之后最容易犯的错：旧写法
`data.get("box", 1)` 在单格时看不出区别，多格之后等于"扫 3 号格、开 1 号格的门"，
用户放进去的东西躺在别人的格里，而页面上写着"3 号"——事后谁都说不清。
贴纸旧了 / 格号写错了，就得当场 404 看出来。

## 管理口令与隐私

监控台（`/`）和两个接口（`/api/orders`、`/api/logs`）**要口令**：

```
http://<局域网IP>:5000/?k=locker-admin        ← 默认口令 locker-admin
```

> ⚠️ 为什么必须挡：订单列表里**有取件码**，而取件码是能开柜的。这两个接口不挡的话，
> 局域网里任何人访问 `http://<IP>:5000/api/orders` 就能捞走所有人的手机号和取件码，
> **整套取件码授权当场作废**。口令在 `app.py` 顶部，用环境变量覆盖：
> `set ADMIN_KEY=你的口令` 再启动。

401 页面**只说"要口令"，不说口令是什么** —— 提示里写出默认口令，等于把钥匙挂在门上，
谁访问一下 `/` 就拿到了。默认口令 `locker-admin` 只写在本文档（给管理员看），
真正演示时建议 `set ADMIN_KEY=自己的口令`，因为源码里那个默认值同学也知道。

**扫码页不查口令**，它只碰三样东西：

- `/api/boxes` —— 柜格状态。不敏感，而且本来就要给用户看门开没开。
- `/api/order/<id>` —— 只回 `id/box/action/status/closed_at/fee_fen`，
  **故意不回手机号、取件码和 store_id**。扫码页只是要盯自己那一单失败了没、
  顺便告诉用户这次花了多少钱，不能让它顺手把整张表捞走。
  `fee_fen` 可以给：它只说明"这一单多少钱"，泄漏不了谁存的、还剩多少余额。
- `/api/pay` —— 自助充值。**故意不查口令** —— 用户自己给自己充，哪来的口令。
  代价是局域网里任何人知道手机号就能给它充值。课设里钱是假的，无所谓；
  真实上线这条必须由**支付平台的回调**驱动，绝不能让客户端说了算。
  详见上面「扣费」一节里的 ⚠️。

另外，**扫码页不把手机号存进 localStorage**。这是共用柜子，页面每次打开都该是干净的 ——
存下来的话，下一个人扫同一个码，输入框里就躺着上一个人的手机号。

## 授权（防越权）

| 路径 | 凭证 | 校验 | 格号从哪来 |
|---|---|---|---|
| H5 存件 | 手机号 | 必须在 `users` 表里注册过 | 柜格贴 → 就是那一格；总码 → `pick_free_box()` 挑在线空格 |
| H5 取件 | **6 位取件码** | 必须对上某一格里那件东西的 `pickup_code`，否则 403 | 柜格贴 → 就是那一格；总码 → `box_of_code()` 逐格找 |
| 刷卡 | 校园卡 UID | 卡主**占着某一格**就取那一格；没占就从在线空格挑一格存 | 后端按卡主算，**报文里的格号被忽略** |

三条路最后都归到同一个问题：这一格里现在是空的吗 —— 由 `occupant()` 一个函数回答，
全项目没有第二个口径（见上面「多格」一节）。

存件成功后页面大字显示取件码（刷卡存件的码在监控台看）。取件**不校验是谁来取**——
码就是凭证，朋友拿码也能取走，这是有意的。

## 扣费

寄存不是免费的。**费用全部在后端算，固件一行没改** —— 设备只是个开锁执行器，
它不知道钱的事。

### 规则

| 项 | 值 | 环境变量 |
|---|---|---|
| 计费起点 | 存件订单的 `closed_at`（门关上那一刻） | — |
| 免费时长 | 30 分钟 | `FREE_SECONDS=1800` |
| 计费单位 | 每满 1 小时；不足 1 小时按 1 小时算 | `UNIT_SECONDS=3600` |
| 单位价 | ¥1 | `UNIT_FEE_FEN=100` |
| 单次封顶 | ¥10 | `MAX_FEE_FEN=1000` |
| 结算时点 | 取件订单变 `done`（门再次关上） | — |
| 计费对象 | **存件人** `orders.phone`（不是取件人） | — |
| `failed` 订单 | 一律不收费 | — |

举例：存了 2 小时 → 计费 (7200−1800)=5400 秒 → 上取整 2 个单位 → **¥2**。
存了 40 分钟 → 600 秒 → 1 个单位 → **¥1**。存了 25 分钟 → **免费**。

金额**全程用整数分**，绝不碰浮点。`compute_fee()` 是纯函数，看见入参就知道结果。

### 余额、欠费与充值

每个用户有 `users.balance_fen`（整数分，`NOT NULL DEFAULT 0`）。**首次加这一列时**
给已存在的用户发 ¥50 启动余额 —— 这条 `UPDATE` 写在建列的 `if` 里面，所以**重启不会
把花掉的余额重置**（测过了，见下面的验证清单）。

- **两条充值入口**：
  - **用户自己充** —— 扫码页「我的」里三个按钮（`POST /api/pay`），**模拟支付**。
  - **管理员代充** —— 监控台钱包面板（`POST /api/recharge`，要口令）。

  两笔都走同一个 `recharge()`，流水的 `note` 区分来路（`模拟支付` / `管理员充值`）。
  **用户端这一条是必须有的** —— 不然欠费的人自己走不出来，只能去找管理员，
  "欠费冻结"就成了一个死循环。

  > ⚠️ `/api/pay` **不做任何身份校验**：知道手机号就能给它充值。这跟 `/api/open`
  > 的现状一样（也只认手机号），所以并没有比原来更弱。但真实上线必须换成
  > **支付平台的异步回调 + 签名校验** —— 不能让客户端说充多少就是多少。
  > 课设里钱是假的，这一步的意义是把"充值"这个动作演完整。
- **余额不足时允许取件，余额扣成负数** —— 东西必须能取出来，扣在柜里比欠费更糟。
- **欠费后冻结的是"存件"，不是"取件"**：`/api/open` 走存件分支会返回 **402**，
  刷卡存件会回 `{"result":"deny","reason":"balance"}`。取件两条路都不拦。

### 费用是怎么挂上去的

取件单要知道它取的是**哪一单存件**，否则算不出放了多久。这个链接是 `orders.store_id`：

- 存件单不带 `store_id`（为 NULL）。
- 取件单在**创建时**就写上 `store_id`，两条创建路径都写：
  `api_open()` 的取件分支带 `occ["id"]`，`handle_card_scan()` 带
  `occ["id"] if action == "pickup" else None`。

> ⚠️ **不能拿 `box + phone` 反推存件单 —— 现在也不行。** 以前是因为 `box` 恒为 1、毫无区分力；
> 现在有四格了，但**一个人可以同时占好几格**（每次存件都是显式给格号的），
> `box + phone` 仍然指不回"哪一单"。只有 `store_id` 这一条链接是准的。

扣费发生在 [`handle_device_event()`](backend/app.py) 的 `door_closed` 分支里：
`advance(box, OPENED, DONE)` 之后调 `settle_pickup(oid)`。两者**不在同一个事务里**，
所以进程如果在中间被杀，那条取件单就白取走了 —— 兜底是 `sweeper()` 每 2 秒扫一次
"`done` 了但没有对应 `charge` 流水"的取件单，补上。

幂等靠两条一起保证：`ledger` 上的**部分唯一索引**
`ux_ledger_charge_order ON ledger(order_id) WHERE kind='charge'`，
外加 `settle_pickup()` 进来先查一次流水。重复的门磁回执不会重复扣钱。

**免费的单也会落一条 0 元的 `charge` 流水** —— 补账扫描的判据是"有没有流水"，
不落的话那单会被 sweeper 每 2 秒重算一次，没完没了。

### 几个必须守住的写法

- **扣费必须用 `tx()`（`BEGIN IMMEDIATE`），不能用 `conn()`。** 读余额 → 减 → 写回 →
  记流水是一串"先查后写"，autocommit 连接挡不住并发。
- **绝不能在 `tx()` 里调 `audit()` / `db()` / `conn()`。** 它们会另开一条连接，
  而这里正握着写锁 —— 等于自己等自己，卡到 `busy_timeout` 超时才报错。
  所以 `settle_pickup()` 只返回一个 dict，审计由调用方在事务外面写。
- **NULL 会把 `NOT IN` 整锅端掉。** 补账扫描的 `id NOT IN (SELECT order_id FROM ledger ...)`
  必须显式加 `order_id IS NOT NULL`：子查询里只要有一个 NULL，整个比较全变 unknown，
  **所有**行都会被判为"不匹配"。

### 演示：同一套规则，只是跑得快

四个阈值都是环境变量，所以**逻辑路径一模一样**，只是把秒数压小：

```bat
set FREE_SECONDS=6
set UNIT_SECONDS=6
set UNIT_FEE_FEN=100
.venv\Scripts\python.exe app.py
```

免费窗口从 30 分钟变成 6 秒，一个计费单位也从 1 小时变成 6 秒。现场的观感是：
存件 → 门关上 → 监控台那行费用从 `≈¥0.00` 开始**当场往上跳** → 取件 → 定成 `¥2.00`，
余额同步扣掉。老师不用等两小时。

**页面上写的规则是从后端注进来的**（`/scan` 和 `/` 都带 `pricing`），
所以演示模式下扫码页会显示"6 秒内取走免费"，不会写着"30 分钟"骗人。

一步步的演示脚本见 [`docs/演示脚本.md`](docs/演示脚本.md)。

## 运营看板（`/api/stats`）

监控台顶部那排数字，全是**只读聚合**（没有"读-改-写"，用 `conn()` 就够，不需要 `tx()`）：

| 指标 | 口径 |
|---|---|
| 今日营收 | 今天已结算的 `charge` 流水之和（**含免费单的 0 元**）|
| 今日寄存 | 今天创建的 `store` 单数 |
| 当前在柜 | `occupant()` 数出来的非空格数 / `BOX_COUNT` |
| 平均寄存 | 今天已 `done` 的取件单，**取件关门时刻 − 存件关门时刻**的平均值 |
| 封顶单 | 今天 `amount_fen <= -MAX_FEE_FEN` 的扣费条数 |

⚠️ **平均寄存时长取的是两个 `closed_at` 之差，不是 `created_at`。**
计费用的就是这两个关门时刻（`elapsed_seconds`），看板必须和计费**同一个口径** ——
否则页面上"平均 3 分钟"和"这一单扣了 ¥3"会互相打架，而两个数各自看着都对。

接口**要口令**（和 `/api/orders` 同一把 `ADMIN_KEY`）：营收、单量都是经营数据，
不该跟着扫码页一起敞开。日期按**服务器本地时区**的 `YYYY-MM-DD` 切，不做时区换算。

## 已知缺口（没做 / 已知风险）

按重要性排，课设答辩时**主动说**比被问出来好：

1. **MQTT 没有设备身份 —— 最该补的一条。** broker 只有一个账号（`locker`/`locker123`），
   后端**无条件相信** `locker/<DEVICE_ID>/status` 和 `/event` 上来的任何报文。
   后果：局域网里任何一个拿到这对账号的人，都能假装成柜子往 `event` 里灌
   `door_closed`（凭空把订单推成 `done`、触发计费）或灌假 `status`（伪造在线）。
   后端还只能用 `last_seen` 判断"最近有没有收到报文"，区分不了**是不是同一台设备**。
   要补的话是三层：① 每台设备一个账号 + broker 的 ACL（只准发自己的主题）；
   ② 报文里带设备 ID/序列号，后端校验；③ 关键命令带 nonce 防重放。
   **本次没做**，`DEVICE_ID` 在两侧都还是写死的常量 `locker1`。
2. **`advance()` 按格推进、不按单**（时序竞态，详见「多格」那节的 ⚠️）。
   根因是门磁回执里没有订单号。修法是把 `cmd` 里的 `order` 让固件回传。
3. **取件码是 6 位纯数字，全局唯一但可枚举。** `gen_pickup_code()` 在
   `BEGIN IMMEDIATE` 里扫全表保证不重复，但没有**尝试次数限制** ——
   理论上可以拿脚本刷 `/api/open?action=pickup&code=...` 撞别人的码。
   课设里没人这么干，真实上线得加限流 + 冻结策略。
4. **扫码 / 刷卡那条路只认手机号，没有登录态。** 知道手机号就能替它存件；
   `/api/pay` 同样是只要知道手机号就能充值（见「扣费」里的 ⚠️）。
   真实上线这两条都得有身份认证。
5. **`BOX_COUNT` 默认 4，但真机只装了 1 号格** —— 监控台上 2~4 号格会显示离线。
   这是**预期行为**，不是故障；要干净地演示单格就 `set BOX_COUNT=1` 且模拟器 `--boxes 1`。
6. **实物上的 2~4 号格是没有门的格子**（只有 1 号格接了舵机和锁）。
   演示时那几格的"开门"是固件演的，**柜门不会真的动** —— 这一点要主动讲清楚，
   别让人以为在演假动作。
7. **秤判错这一层，两条新机制都盖不住 —— 这是目前最该补的一条。**
   「真机格对账」只自动修"DB 说有物、秤说没有"这一个方向（反向只报警，不动数据）。
   更要紧的是**秤自己判错**：存件时若关门后那次采样**漏判**（东西确实放进去了，
   但 800ms 后那一次读数没到门限），固件会落 `IDLE`、后端把单判 `failed` ——
   两边**一致地**说"这格是空的"，东西却真在格里，**既没有订单也没有告警**，
   要等下次开这格才发现。（反过来"没放东西却判成有物"现在能被对账修掉。）
   治本是**关门判定前等读数稳住再判**（连续两次采样靠拢、最多等 2 秒）——
   ⚠️ **本次没做**。根因是门关瞬间秤还在振铃，而门限 `ITEM_THRESHOLD_COUNTS = 8000`
   实测有读到 −9382 的例子，**余量只有 1.17 倍**（见「物品检测」一节）。

## 踩过的坑

1. **Mosquitto 2.x 默认只绑本机 + 禁匿名** —— 见上面第 1 节，不处理手机和 ESP32 都连不上。
   另有一个更隐蔽的：**密码文件权限不对会让服务启动后秒退**（`net start` 还报"启动成功"），
   原因和一行解法见第 1 节末尾的 ⚠️。
2. **MFRC522 只吃 3.3V**，接 5V 直接报废。
3. **SG90 堵转电流约 700mA**，接开发板 5V 容易把 ESP32 拉重启；现象是"一开锁就复位"，此时给舵机单独供电。
4. **手机和电脑必须在同一网段**，URL 不能写 `localhost`。校园 WiFi 若开了**客户端隔离**（AP isolation），手机连不上电脑，需换热点或找管理员。
5. **Windows 防火墙**默认拦 5000 端口，手机打不开页面先查这里。
6. **不要同时跑两个常驻模拟器或两个同 `DEVICE_ID` 的设备**，它们的 `status` 会互相覆盖，
   状态看起来会乱。（`--card` 那个注入器不受影响，它的 `client_id` 带了进程号，
   不会顶掉常驻进程 —— MQTT 规定 `client_id` 相同即踢掉旧连接。）
7. **判断设备在线，只能用后端收到报文的时刻，绝不能用报文里的 `ts`**。
   固件发的 `ts` 是 `millis()/1000`（开机秒数，几十到几百），
   模拟器发的 `ts` 是 `int(time.time())`（Unix 秒，17 亿多）。两者语义完全不同。
   拿它算在线，真机一上线就被判离线。后端因此另存了 `last_seen = time.time()`，
   而且**只在 `status` 心跳里刷新** —— 事件消息不刷，否则一条 `card_scan`
   就能让已经死掉的设备"续命"。
8. **在 Git Bash 里用 `curl -d` 发中文会失败**，但这不是后端的锅。Git Bash 的 curl 按
   **GBK** 把中文编进请求体，而后端按 UTF-8 解 JSON，解不开 → Flask 的
   `get_json(silent=True)` 返回 `None` → 整个 body 变成空字典，
   于是 `{"name":"李四",...}` 会诡异地报"请填姓名"。**用 Python 发就没这问题**
   （见上面 `/api/register` 的接口说明），浏览器更没问题。手工测中文时记得绕开 curl。
9. **改 `templates/*.html` 后页面没变化？** Flask 在 `debug=False` 时**会把模板缓存住**，
   不重启进程看不到效果，很容易误以为改错了文件。`app.py` 里已经加了
   `TEMPLATES_AUTO_RELOAD = True` 修掉它。要是哪天被删了，症状就是"死改没反应"。
10. **压力传感器"没有绝对零点"，所以"重启时必须空着托盘"是硬要求。** 零点就是开机
   那一下取的（去皮），托盘上有东西时重启，那东西会被当成零点，之后一直报"空"，
   而且**光看屏幕看不出来**——它显示的就是"无物"，一切正常的样子。自救是串口敲 `t`
   重新去皮，或者清空托盘重启。详见上面「物品检测」一节。
   （换压力传感器之前这里记的是**光电 DO 极性因模块而异**那条：那版模块是"挡住才拉高"，
   而固件原以为"检测到物品拉低"，于是空柜读成"有物"、放进东西读成"无物"，**两个方向同时反**，
   防呆会反着拦、整条状态机倒着走。换传感器后这条不再适用，但教训一样：
   **物品检测的语义一定要拿实物在实机上正反各测一遍**，别信接线图。）
11. **舵机开锁不等于柜门被打开 —— 这条只有真簧片开关才暴露。** 详见上面「状态机」一节
   的 ⚠️。之前拿跳线模拟门磁时，GPIO 4 悬空一直读"开"，等于替你把门"开"着，
   关门回执要等你接地才来，**恰好把这个竞态完全掩盖了**。接上真簧片当天就复现：
   订单 `door_opened → door_closed` 只隔 **1 秒**，正常的应该隔好几秒（人的操作时间），
   拿这个间隔当判据最快。修法是固件里的 `doorSeenOpen`：没见过门开，就不认门关。
12. **HX711 的 VCC 接成 5V（本该 3.3V）会把整块 ESP32 报废 —— 2026-10-12 实测过一次。**
   机理是一条链，不是只烧一个脚：红色小板 VCC 与 DVDD 短接 → VCC=5V 时 DOUT 就输出 5V →
   直怼 GPIO 27，**这根线上没有任何限流** → GPIO 打穿后芯片闩锁，从 3.3V 轨抽大电流 →
   板载 AMS1117 过载、3.3V 轨塌掉 → 而这类板子的 **CH340 吃的正是同一条 3.3V**，跟着一起死。

   **现象很好认，而且反过来能定位问题**：插上电脑后**连串口都不出现**。
   `Get-PnpDevice -Class Ports -PresentOnly` 返回空，CH340 只剩一条 `Present: False`、
   问题码 **Code 45（CM_PROB_PHANTOM）** 的注册表残影，`esptool` 打开端口报"找不到指定的文件"。
   判据是：**如果只是 ESP32 程序跑飞或芯片本身死了、而供电还正常，COM3 一般还在**
   （端口能打开，只是 esptool 同步不上）。连 COM 口都没了 → 问题在 USB/供电段，不在 MCU。

   **换板子前先加这两道保险**：
   ① 上电前**先只接 VCC 和 GND**，确认插在 `3V3` 脚上 —— 30-pin 板上 `3V3` 和 `5V`(VIN) 挨着，
   这次就是这么插错的。
   ② 在 **DT 和 GPIO 27 之间串一个 1kΩ 电阻**。再插错 5V 时灌进 ESP32 的电流被限到 1mA 量级，
   靠芯片内部钳位二极管就扛得住。3.3V 供电下本来不需要它，纯粹是保险，**且不用改代码**
   （`INPUT_PULLUP` 照样工作）。

   **别把 HX711 和称重传感器一起扔了** —— HX711 额定 2.7–5.5V，被供 5V 完全在范围内，
   被打坏的只有 ESP32 那一侧的输入。
13. **`WiFi.mode(WIFI_STA)` 卡死不动，根因是 USB 供电不够 —— 2026-10-16 实测过一次。**
   换上新板子后整套固件**卡在 `WiFi.mode(WIFI_STA)` 这一行**：串口打完上一句就再没下文，
   屏幕停在"准备连 WiFi"。这个症状很能骗人，三条都指向"不是代码的问题"：

   - **没有 brownout 提示、没有看门狗复位、没有重启横幅** —— 是**真卡住**，不是掉电重启；
   - 整片 `erase_flash` 后重烧**照样卡**，所以不是 NVS 里的脏数据；
   - 写一个**只含 `Serial` + `WiFi`、一个外设都不接**的最小草图，**卡在同一行**
     —— 这一条把固件、HX711、RC522、舵机、OLED 全部排除干净。

   根因是**射频启动那一下的电流峰值**（500mA 量级）。它之前的一切（启动、串口、flash 读取）
   只要 100mA 上下，所以现象正好是"能开机、一开 WiFi 就死"：电压被拉到**刚好不触发 brownout
   （约 2.4V）却不够 PHY 完成校准**，于是**静默卡死**。换一个能供上电的 USB 口/线之后，
   同一个调用**瞬间返回、1.5 秒连上**。细线、长线、走 HUB 都容易掉在这一档。

   > **排查"卡在某一行"的通用手法：先用最小草图把问题一分为二。**
   > 外设全不接还卡 → 问题在板子/供电/子系统，跟代码无关；不卡 → 是前面哪一步把它弄坏的。
   > 花 5 分钟，方向就定了，比逐段注释快得多。

   同一轮里 HX711 还报过"读不到"（DT 一直不拉低），换完供电自己就好了 —— 3.3V 轨塌的时候
   它也没起来。**这两条大概率是同一个根因**，但当时没做隔离实验，只作现象记录，不当结论。
14. **MFRC522 克隆片报 `0x82`，不是坏 —— 别把版本号写死成 `0x92`。**
   固件原来写 `ver == 0x92 ? "正常" : "异常"`，于是这块**读卡完全正常**的模块
   在屏幕上一直显示**「读卡器 0x82 异常」**（实测能读到卡号 `6B492D54`）。
   判据应该是"**芯片答没答话**"，不是"版本号是不是教科书上的值"：
   **只有 `0x00` / `0xFF` 才代表 SPI 压根没通**（那才是接线或供电问题），其余都算正常。已修。
   教训同坑 10：**判据要拿实物验，别照着数据手册写死。**
